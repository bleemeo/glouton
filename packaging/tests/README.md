# Debian packaging tests

Regression tests for the Debian maintainer scripts in `packaging/scripts/`
(`preinstall.sh` → `preinst`, `postinstall.sh` → `postinst`, `preremove.sh` → `prerm`,
`postremove.sh` → `postrm`).

These scripts are hand-written rather than generated by `debhelper`, so nothing else
verifies that they keep `deb-systemd-helper`'s bookkeeping consistent across
install / upgrade / remove / purge. That bookkeeping is what
[PRODUCT-3181](https://bleemeo.atlassian.net/browse/PRODUCT-3181) got wrong: a purge left
`/var/lib/systemd/deb-systemd-helper-enabled/glouton.service.dsh-also` behind, and a later
install then refused to start Glouton.

## Running

```sh
./packaging/tests/run.sh                       # the full matrix
./packaging/tests/run.sh --scenario purge-reinstall
./packaging/tests/run.sh --old-ref <git-ref>   # compare against a different baseline
./packaging/tests/run.sh --keep                # keep failed containers to poke at
```

Requires Docker. Roughly a minute for the full matrix; the image is cached after the
first run.

### Also testing the real package

The matrix uses a stub package (see below). To additionally smoke-test a real
goreleaser-built `.deb`:

```sh
GOOS=linux GOARCH=arm64 ./build.sh single-target skip-js skip-test skip-docker
./packaging/tests/run.sh --deb dist/glouton_*_linux_arm64.deb
```

Use `GOARCH=amd64` on an Intel machine. The real-package run installs a
`bleemeo.enabled: false` drop-in first, so the agent starts standalone without
credentials.

## How it works

Each scenario gets a **fresh Ubuntu 24.04 container running systemd as PID 1**. Real
systemd matters: without `/run/systemd/system` the postinst skips its whole
enable/restart path, and every assertion would be vacuous.

Two packages are built and compared:

- **old** — maintainer scripts read from `--old-ref`, which defaults to the commit right
  before this fix. It is pinned to a SHA rather than to `main` on purpose: once the fix is
  merged, `main` carries it too, the rows expected to fail would all pass, and the suite
  would report failure forever. Point it at whatever baseline your change needs.
- **new** — maintainer scripts from your working tree

Both carry the *real* scripts and the *real* `packaging/common/glouton.service`; only the
Go binary is stubbed (`exec sleep infinity`). The bug lives entirely in the scripts and in
`deb-systemd-helper`'s state machine, so the binary is irrelevant and stubbing it keeps
each iteration to a couple of seconds.

**The suite asserts that the old scripts fail.** `purge-clears-state` and
`purge-reinstall` are expected to fail against the baseline — that is the reproduction. If
they start passing, the bug is no longer being reproduced and the green results for the new
scripts prove nothing, so `run.sh` reports that as an error rather than as success.

## Scenarios

| Scenario | What it does | old | new |
| --- | --- | --- | --- |
| `fresh-install` | install on a clean machine → running and enabled | pass | pass |
| `upgrade` | install v1, then v2 → still running | pass | pass |
| `upgrade-honors-disable` | install, `systemctl disable`, upgrade → must stay disabled | pass | pass |
| `purge-clears-state` | install, purge → no `deb-systemd-helper` state left | **fail** | pass |
| `purge-reinstall` | install, purge, install → must be running | **fail** | pass |

The last two are PRODUCT-3181 itself: the leftover state file, and the "installed but
doesn't start" that follows from it. The first three are there so the fix cannot buy those
two at the cost of the ordinary paths — in particular `upgrade-honors-disable`, since a
deliberate `systemctl disable glouton` must survive an upgrade.

Scope is deliberately narrow. Several neighbouring gaps were found while investigating
this ticket — `apt remove` + reinstall, hosts already broken before the fix ships, and
`glouton-auto-upgrade.timer` — and are written up for separate tickets rather than tested
here.

## Notes on the container

- `--privileged` is needed for systemd as PID 1. On macOS it applies to the Docker Desktop
  VM, not to your workstation. No host directory is bind-mounted — the packaging files are
  baked into the image with `COPY` — and containers get `--cgroupns=private` with no host
  cgroup mount, which is enough for systemd on cgroup-v2-only Ubuntu 24.04.
- The image deletes `/usr/sbin/policy-rc.d`. Ubuntu's Docker images ship it containing
  `exit 101` so that installing a package never starts its daemon during an image build.
  `deb-systemd-invoke` honours that policy, so leaving it in place would make every
  "did Glouton start?" assertion fail for a reason unrelated to the code under test. A
  real Ubuntu 24.04 host has no such file.
- Containers are named `glouton-pkgtest-<variant>-<scenario>` and removed on completion
  (`--keep` retains the failed ones).

## Scope

Debian/Ubuntu only. The RPM paths in the same scripts (the `0` / `1` / `2` argument
branches) are not covered here.
